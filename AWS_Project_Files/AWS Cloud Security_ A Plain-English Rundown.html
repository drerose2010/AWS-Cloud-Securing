Securing what you build on AWS

Amazon Web Services lets you rent computing, storage and databases on demand. Security in that world is a partnership. This page explains who protects what, and the tools that do the work.

Start the rundown

What is AWS?

AWS is a collection of over 200 services delivered over the internet. Instead of buying servers, you create them in minutes and pay for what you use.

  • Regions and Availability ZonesData centres are grouped into geographic Regions, each split into isolated zones so one failure does not take everything down.
  • Services on demandVirtual servers (EC2), storage (S3), databases (RDS) and many more, all managed through the console, CLI or code.
  • Security built in, not bolted onIdentity, encryption and monitoring are first-class services you switch on and configure.

The shared responsibility model

The most important idea in AWS security. AWS secures the cloud itself. You secure what you put in it.

Core security services

A starter map of the services you will meet first.

IAM

Controls who can do what. Users, roles and policies that grant least-privilege access.

KMS

Creates and manages the encryption keys that protect data at rest in S3, EBS, RDS and more.

GuardDuty

Threat detection that watches logs and network activity for suspicious behaviour.

CloudTrail

Records API calls across your account, so you can answer who did what, and when.

Security Hub

Pulls findings from many services into one place and checks them against best-practice standards.

WAF & Shield

Filter malicious web traffic and absorb DDoS attacks before they reach your applications.

Think in layers

Good AWS security stacks several controls. If one fails, another still stands between an attacker and your data.

Identity decides who gets in, network rules limit what can talk to what, encryption protects the data itself, and logging plus alerts tell you when something looks wrong.

Five habits worth building early

Most cloud incidents trace back to a misconfiguration rather than a clever exploit.

  1. Turn on MFA for the root user and every human account, and avoid using root day to day.
  2. Grant least privilege. Start with no access and add only the permissions a role needs.
  3. Block public S3 access by default and make exceptions deliberately.
  4. Encrypt data at rest with KMS and in transit with TLS.
  5. Log everything with CloudTrail and review findings in GuardDuty and Security Hub.
